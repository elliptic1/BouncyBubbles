## Build, test, run

Single-module Gradle Android project (AGP 8.5.2, Kotlin 2.0.21, JDK 17, `compileSdk = 34`, `minSdk = 26`). Versions are pinned in `gradle/libs.versions.toml`.

```bash
./gradlew :app:assembleDebug              # debug APK
./gradlew :app:installDebug               # install on connected device
./gradlew :app:testDebugUnitTest          # all unit tests (JVM, no device)
./gradlew :app:testDebugUnitTest --tests "app.toddbsmith.bouncybubbles.physics.PhysicsEngineTest.elasticCollision_equalMass_swapsVelocities"
./gradlew :app:lintDebug
```

The Gradle wrapper jar is generated by Android Studio on first sync — if `./gradlew` fails because `gradle/wrapper/gradle-wrapper.jar` is missing, open the project in Android Studio once.

Release signing reads from `keystore.properties` (gitignored). If absent, the release build falls back to debug signing — that's intentional, don't add unconditional `signingConfig` lookups in `app/build.gradle.kts`.

The accelerometer-driven gravity only works on a real device. Emulators report a static gravity vector and the bubbles will just sit there.

## Architecture

This is a system-wide overlay app, not a normal activity-based one. The launcher Activity exists only to grant permissions and start the foreground service; **all the interesting code lives in the service**.

### The "per-bubble window" model (read this before touching the overlay)

Each bubble is its own tiny `WindowManager` overlay window, sized just larger than the bubble and positioned by absolute `params.x`/`params.y`. The FAB is another window. The dismiss zone is a third (attached only mid-drag). This is intentional — a single full-screen overlay would intercept every touch and break the phone underneath. With per-bubble windows, touches outside any bubble fall through to the OS / app below, so the phone stays fully usable while bubbles float on top.

Consequences to keep in mind when modifying `overlay/`:

- Window params use `gravity = TOP|START` + `FLAG_LAYOUT_NO_LIMITS`. Under that combo, `params.x`/`params.y` are **absolute top-left in raw screen pixels**, not the density-corrected "extra offset" some docs describe.
- Every visual position update is a `windowManager.updateViewLayout(view, params)` call from the frame loop. The frame loop short-circuits when `params.x`/`params.y` haven't changed for a bubble — preserve that guard.
- `BubbleView.SLACK_PX` is the transparent gutter around each bubble window so the drawn bubble (with shadow/glow) isn't clipped by the window bounds. Window size = `2*radius + 2*SLACK_PX`. If you change rendering, keep this invariant.
- The FAB is registered both as a draggable view (`FabView`) AND as a `StaticObstacle` in the physics engine, so bubbles ricochet off it. When the FAB moves, `updateFabObstacleFromScreenPosition()` must run.
- The dismiss zone is `FLAG_NOT_TOUCHABLE` — it's purely visual; the "did the user drop a bubble on the X" decision is made by distance check in `onBubbleDragEnd`.

### Frame loop

`BubbleOverlayService` implements `Choreographer.FrameCallback`. Each frame:

1. `engine.step(dt)` — physics
2. For each bubble: diff-then-update window layout (skip if unchanged)
3. Dismiss-zone proximity + tick its animation
4. `view.invalidate()` only for bubbles that need a *redraw* (popping, spawning, or being dragged) — passive motion just needs a window-move, not a repaint.
5. Reconcile: any window whose `Bubble` is no longer in `engine.bubbles` (popped out by physics) gets removed.

`dt` is clamped to a 30 Hz floor to keep physics stable when the system stalls.

### Physics (`physics/PhysicsEngine.kt`)

Hand-rolled 2D, no library. Semi-implicit Euler with sub-stepping (default 4 substeps per frame — prevents tunneling at high speed). Mass = `radius²` (area-proportional). The engine has no knowledge of touch, rendering, or Android — it just owns `bubbles`, `obstacles`, gravity, and bounds. `PhysicsEngineTest` exercises `resolvePair` directly, which is why that function is `internal` rather than `private`.

Drag behavior is **1:1 finger tracking** (see commit `27530a8`): while `beingDragged`, integrate() teleports the bubble to `(targetX, targetY)` every substep and zeros velocity. There's no spring. On release the service writes the touch-sampled fling velocity directly into `vx`/`vy`. If you reintroduce a spring or any lag here, you'll regress the "true fling" feel.

Gravity comes from the accelerometer in `onSensorChanged`, low-pass filtered (`gravityAlpha = 0.85`) and rotated into screen space based on `Display.rotation`. Don't skip the rotation switch — landscape will feel wrong otherwise.

### Tunables passed from launcher → service

`MainActivity` collects `LauncherSettings` from `LauncherScreen` (Compose) and passes them via intent extras (`EXTRA_INITIAL_COUNT`, `EXTRA_RADIUS_MIN_DP`, `EXTRA_RADIUS_MAX_DP`, `EXTRA_GRAVITY_SCALE`, `EXTRA_BOUNCINESS`). `gravityScale` multiplies a base of `800 px/m`. `bounciness` is clamped to `0.5..0.95` and becomes `engine.restitution`. `MAX_BUBBLES = 25` is a hard cap enforced in `spawnBubbleAtRandom()`.

### Permissions

`SYSTEM_ALERT_WINDOW` is the load-bearing one — without it the service immediately `stopSelf()`s. `MainActivity` polls `Settings.canDrawOverlays()` every 400ms so returning from the system settings screen updates the launcher UI without a manual refresh. `POST_NOTIFICATIONS` (API 33+) is requested when the user taps Launch; declining is fine, the FGS still runs. The foreground service type is `specialUse` with a `PROPERTY_SPECIAL_USE_FGS_SUBTYPE` property — required on API 34+.

## Conventions worth knowing

- `BubbleOverlayService.running` is a `@Volatile var` with a private setter; the launcher reads it to show "Running"/"Stopped". Keep it in sync with `attached`/`tearDown()`.
- The service must be tolerant of `windowManager.removeView` / `updateViewLayout` throwing on already-detached views — wrap in try/catch (see `safeRemove`). Don't replace these with assertions.
- This project does **not** use Hilt, Compose Navigation, ViewModels, coroutines for the overlay loop, or any DI. The only Compose surface is the launcher screen. Don't pull these in unless there's a real need.
